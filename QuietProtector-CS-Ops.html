1.5

Golden rules — read first

These override default behavior. If a later section seems to conflict with one of these, this section wins.

  1. All refunds are processed in CheckoutChamp, never Shopify. Shopify “refunds” never move money. Exception: direct-Shopify sales (§3.7).
  2. Sequence every refund: log → dispute-check → refund. Never refund immediately on request — refunding on top of a live chargeback alert double-credits the customer.
  3. Before any refund, check ChargeBlast, PayPal, and the processor for an active alert or dispute. If one exists, do not issue a standard refund — go to the dispute workflow (§07).
  4. Disputes outrank the email queue. Work dispute-related orders before general tickets.
  5. Every COO escalation includes customer name, email, and order number. “No context means no understanding.”
  6. Reference orders by CheckoutChamp order number (QP…) or customer email — never by transaction ID. CC cannot search by transaction ID.
  7. Every refund gets a written reason note in CheckoutChamp (order page → “Add Note”). An un-noted refund is unauditable at month-end.
  8. Try to recover before you cancel. State the retention discount directly in your reply — don’t just send the self-service link. See §3.3.
  9. Never make the customer wait for a judgment call you can look up. Where this SOP gives a decision tree, follow it. Escalate only genuinely new situations, with case data attached.

2.1

Master Refund Decision Tree

!
ImportantUniversal exception — overrides every ladder below. If a customer explicitly demands a full refund, don’t counter with a token low-end discount — offer a real choice (“15% or a full refund”) or just refund. “We do not want to piss off someone that’s already pissed off.”
2.2

Master refund process (every refund, every transaction type)

  1. Log. Log the request first, before any action, in the Refund/Dispute Log: docs.google.com/spreadsheets/d/18uCU867h3d7mXlcO6c84Nz7p-XI_dZsvbBv8amLnhE4/edit?gid=1649811498 (NewCallHQ phone team fills columns A–F only).
  2. Dispute-check. Check the processor/Kurv, PayPal, and ChargeBlast for an active alert/dispute on that card.
  3. Decision. Clean → dispute-checker signs off on the sheet; refund processes next shift. Dispute/alert exists → do not refund standard; escalate to §07.
  4. Refund. Process in CheckoutChamp only. Double-check state (pending vs. processed) — PayPal refunds via CC can hang “pending.”
  5. Note. Add a refund-reason note on the CC order page (“Add Note”) — mandatory for analytics.
!
ImportantWhy log-first matters: with chargeback alerts running, an instant refund on top of a live bank chargeback is a duplicate credit. The log step catches that before money moves.

CheckoutChamp vs. Shopify

Process every refund in CC. If you find a Shopify-side “refund” with no CC counterpart, redo it in CC — the Shopify one moved no money. CC does not email the customer on refund (deliberate — don’t wake sleeping customers); Shopify’s order+refund recap email doubles as processor proof, and the refund reason must also show on the card statement. Address/cancellation edits also do not sync between CC and Shopify.

2.4

Defective, missing & wrong-item claims — canonical workflow

This is the single canonical location for defective / missing / wrong-item refunds. Product Support (§08) and Returns (§05) both reference this section instead of repeating it.

Situation
Customer reports a product doesn’t work, is defective, arrived incomplete, or arrived wrong.
Check
Which of the three applies — the evidence path differs for each.

Decision & action — defective-item path

  1. First response is usage guidance, not a refund ask. Walk the customer through correct use (e.g. TerraStrike’s Press Firmly / Strike Method, §8.2) — most “doesn’t work” tickets are usage, not manufacturing.
  2. If the customer insists it still doesn’t work, ask for a video clearly showing how they’re using the product.
  3. If the customer declines to provide a video → no refund. Firm rule, not agent discretion. Do not offer a discretionary partial refund instead.
  4. If the video clearly shows the product not working, send it to #fulfillment-delivery-complaints and ask Tina to verify. Once Tina confirms, refund/resend proceeds.
  5. Honor whatever was already promised — if an agent already told a customer “send a photo and we’ll refund,” honor that; don’t retroactively demand a video for that specific case.

Structural notes on this restructuring

  • Modules follow the spec’s suggested 01–14 structure with one adjustment: the spec’s example “Order Request Decision Tree” (which triages cancel/modify/address-change/retention/fraud) is the canonical decision point for all order-change requests, so it lives in §03 Order Management; §02 Refunds & Cancellations then owns everything about executing a refund or cancellation once that decision is made (the money side), and links back to §03 for the triage. This keeps “decide what the customer wants” and “process the money” from duplicating each other, per the one-canonical-location rule.
  • The retention/recovery flow (§3.3) is filed under Order Management rather than Refunds, because it’s explicitly a pre-cancellation save attempt, not a refund action — consistent with the spec’s own example, where “changed mind” routes to “RETENTION FLOW” before any refund logic runs.
  • Response templates/tone (§10.7) and the Appendix A/B dispute-routing detail (kept inline in §07 rather than a trailing appendix) were relocated so an agent working a live ticket never has to leave the module they’re in to find the next step — directly serving the “no jumping between unrelated sections” goal.
